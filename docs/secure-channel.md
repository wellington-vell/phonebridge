# Phonebridge secure channel (PBA1)

Authentication and encryption for the audio (control port, default 8125) and
video (control port + 1) TCP connections, and for UDP audio media. It wraps
the existing protocols: after the PBA1 handshake, the unchanged WO Mic
messages (audio) or `PBV1` protocol (video) run inside encrypted records.

Threat model: anyone on the LAN (Wi-Fi mode) or any app on the phone
(localhost ports used by USB `adb forward` and the Bluetooth bridge) can
connect to the phone's ports or impersonate the phone to the PC. Only
someone who knows the pairing code may receive or send media.

Not provided: forward secrecy (a leaked code decrypts recorded sessions;
reset the code on the phone to revoke it).

## Pairing code

- 20 characters from the Crockford base32 alphabet
  `0123456789ABCDEFGHJKMNPQRSTVWXYZ` (100 bits), generated by the phone app
  with a CSPRNG and stored in its private storage until reset.
- Displayed as 4 groups of 5: `ABCDE-FGHJK-MNPQR-STVWX`.
- Canonical form (what the key derivation uses): the 20 characters,
  uppercase, no separators. The PC normalizes user input: drop `-` and
  whitespace, uppercase, map `O`→`0`, `I`/`L`→`1`; then require exactly 20
  alphabet characters.

## Handshake (client = PC, server = phone)

```
C -> S  "PBA1" | Nc (16 random bytes)
S -> C  Ns (16 random bytes)
C -> S  auth_c2s (32 bytes)
S       compares in constant time; on mismatch closes the connection
S -> C  auth_s2c (32 bytes)
C       compares in constant time; on mismatch closes the connection
```

Key derivation, HKDF-SHA256 (RFC 5869):

```
IKM  = canonical code as 20 ASCII bytes
salt = Nc | Ns                      (32 bytes)
PRK  = HKDF-Extract(salt, IKM)
X    = HKDF-Expand(PRK, "phonebridge v1 " + label, 32)   for each label:
  "auth c2s", "auth s2c"   handshake proofs (sent as is)
  "key c2s",  "key s2c"    AES-256-GCM keys of the TCP stream, per direction
  "key udp"                AES-256-GCM key of UDP media datagrams (phone -> PC)
```

Each side waits at most 5 s for each handshake step. The server delays
~1 s before closing after a failed proof (slows online guessing).

## Encrypted TCP records

After the handshake every byte in each direction is carried in records:

```
[len u32 BE][ciphertext | 16-byte GCM tag]     len = ciphertext + tag length
```

- AES-256-GCM, key `key c2s` (PC to phone) or `key s2c` (phone to PC), empty AAD.
- Nonce (12 bytes) = 4 zero bytes | counter u64 BE. Each direction has its
  own counter starting at 0, incremented by one per record. Never reused.
- Plaintext per record: 1..=65536 bytes; writers split larger writes.
  Readers reject `len` < 17 or > 65536 + 16 and any tag failure by closing
  the connection (no partial plaintext is ever delivered).
- The record layer is a byte stream: message boundaries of the inner
  protocol need not line up with records.

## Encrypted UDP media (audio, `--udp`)

When the session is authenticated, each UDP datagram (phone to PC) is:

```
[counter u64 BE][ciphertext | 16-byte tag]
```

AES-256-GCM with key `key udp`, nonce = 4 zero bytes | counter, empty AAD.
The plaintext is the usual V4 media frame. Counters start at 0 and increase
by one per datagram; the PC drops datagrams that fail to decrypt or whose
counter is not greater than the highest accepted one.

## Compatibility

- The PC client without a code (no `--token`) speaks the old plaintext
  protocols, so it still works with the official WO Mic app.
- The phone app requires PBA1 by default. An opt-in setting
  ("Allow clients without the pairing code") makes it also accept plaintext
  clients: the first 4 bytes decide (`PBA1` = secure; anything else is the
  start of a plaintext WO Mic hello / `PBV1` hello).
- An authenticated client replaces the current session only after its
  handshake (PBA1 and the inner protocol hello) succeeded.
